Yes, bro, you’ve understood it correctly. The MONTHLY_DATES CTE serves two purposes:

* Identifies the latest valid Demo–Member Features snapshot pair for each month.
* Assigns a common month-end reporting date (POP_DATE).

We are joining the actual banking tables using MEMBER_ID and their respective DEMO_DATE and FEATURE_DATE, not the artificial month-end date.

For example:

Reporting POP_DATE	DEMO_DATE	FEATURE_DATE

30-Nov-2025	27-Nov-2025	28-Nov-2025

The reporting POP_DATE will then be used to align the task activity.

Single query — Base population + Task population

This combines your already working monthly base population query with the task activity data.

Entirely read-only. No tables are created, modified or published.

WITH DEMO_DATES AS (
    SELECT DISTINCT POP_DATE
    FROM CUSTOMER_DEMO
    WHERE POP_DATE BETWEEN '2025-10-01' AND '2026-10-31'
),
FEATURE_DATES AS (
    SELECT DISTINCT POP_DATE
    FROM MEMBER_FEATURES
    WHERE POP_DATE BETWEEN '2025-10-01' AND '2026-10-31'
),
MONTHLY_DATES AS (
    SELECT
        LAST_DAY(F.POP_DATE) AS MONTH_END,
        D.POP_DATE AS DEMO_DATE,
        F.POP_DATE AS FEATURE_DATE
    FROM DEMO_DATES D
    INNER JOIN FEATURE_DATES F
        ON F.POP_DATE = DATEADD(DAY, 1, D.POP_DATE)
    QUALIFY ROW_NUMBER() OVER (
        PARTITION BY LAST_DAY(F.POP_DATE)
        ORDER BY F.POP_DATE DESC
    ) = 1
),
BASE_POP AS (
    SELECT
        M.MONTH_END AS POP_DATE,
        D.MEMBER_ID,
        D.ACTIVE_IND,
        F.CURRENT_BANKPROD_CNT,
        M.DEMO_DATE,
        M.FEATURE_DATE
    FROM MONTHLY_DATES M
    INNER JOIN CUSTOMER_DEMO D
        ON D.POP_DATE = M.DEMO_DATE
    INNER JOIN MEMBER_FEATURES F
        ON F.MEMBER_ID = D.MEMBER_ID
        AND F.POP_DATE = M.FEATURE_DATE
    WHERE D.ACTIVE_IND = 1
        AND F.CURRENT_BANKPROD_CNT >= 1
        AND D.MEMBER_ID IS NOT NULL
),
MONTHLY_TASKS AS (
    SELECT
        MEMBER_ID,
        LAST_DAY(TASK_DATE) AS TASK_MONTH
    FROM TASK_ACTIVITY
    WHERE TASK_DATE >= '2024-11-01'
        AND TASK_DATE < '2026-11-01'
        AND MEMBER_ID IS NOT NULL
    GROUP BY 1, 2
),
FINAL_POP AS (
    SELECT
        B.*,
        T.TASK_MONTH AS LAST_TASK_MONTH,
        CASE
            WHEN T.TASK_MONTH >= DATEADD(
                MONTH, -11, DATE_TRUNC('MONTH', B.POP_DATE)
            )
            THEN 1
            ELSE 0
        END AS TASK_FLAG_12M
    FROM BASE_POP B
    ASOF JOIN MONTHLY_TASKS T
        MATCH_CONDITION(B.POP_DATE >= T.TASK_MONTH)
        ON B.MEMBER_ID = T.MEMBER_ID
)
SELECT
    *,
    CASE
        WHEN TASK_FLAG_12M = 1 THEN 'POP 1'
        ELSE 'POP 2'
    END AS TASK_POPULATION
FROM FINAL_POP;

Validate the monthly population distribution

Once the above query works, simply replace its final SELECT statement with:

SELECT
    POP_DATE,
    COUNT(*) AS TOTAL_ROWS,
    COUNT(DISTINCT MEMBER_ID) AS BASE_POPULATION,
    COUNT_IF(TASK_FLAG_12M = 1) AS POP_1,
    COUNT_IF(TASK_FLAG_12M = 0) AS POP_2,
    ROUND(
        100.0 * COUNT_IF(TASK_FLAG_12M = 0)
        / COUNT(*), 2
    ) AS POP_2_PCT
FROM FINAL_POP
GROUP BY POP_DATE
ORDER BY POP_DATE;

Important considerations

* Scalability: We aggregate the raw task data before joining. The ASOF JOIN avoids expanding every banking member-month into 12 separate months of task history.
* Date alignment: I am using calendar month-end as the task activity cutoff, even though the banking eligibility snapshot may be a few days earlier.
* Validation: Confirm all 13 snapshots exist, total rows equal distinct members within each month, and the final population counts match your original base population.
* Task scope: We are using all completed tasks, not just Consumer Lending tasks. I assume your task table already contains completed tasks only.
* Transactions: Not incorporated yet.

Our next step, after validating this dataset, will simply be a member-level comparison across consecutive months to identify Pop 1 → Pop 2 and Pop 2 → Pop 1 migrations.
